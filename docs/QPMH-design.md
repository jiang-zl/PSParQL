# PSParQL 单查询边分桶设计与验证方案

设计基线为 `revise@4079ce5`。范围是一条连通 BGP、固定谓词、顶点常量和变量。沿用现有数据分区、RDF 同态语义和精确回溯。目标是验证 WISE 的候选边分桶能否通过共享后续工作降低分布式查询耗时。本文保留实验前的设计，文中的工作量示例来自离线集合枚举。实际交付的策略、阈值、四个查询的实测收益及偏差见[实现与实验结果](../benchmarks/results/qpmh/README.md)。

## 1. 从查询边到任务归属

WISE §4 的分组对象是第一条有向查询边的候选数据边。对候选边两端，分别按查询所需属性取邻居集合。定义 4 用这些集合间 Jaccard 相似度的乘积刻画相似性，定义 5 从各集合取最小哈希形成向量，算法 2 用该向量安排任务。分桶只影响工作共享，精确求交和结果枚举仍决定答案。

当前实现选择了起始查询边，但 `GMatchComper::task_spawn(v)` 对单个数据顶点的全部邻居 ID 生成签名，查找计算线程本地的待执行任务。`graph_matching_root()` 从一个根绑定进入递归。`Worker` 对被窃取任务的 `to_pull` 做哈希属于另一个调度阶段。要验证 WISE，必须贯通起始边绑定、双端签名、跨 rank 归属和双端起步的枚举。

| 阶段 | 对现有代码的具体修改 | 必须满足的条件 |
|---|---|---|
| 计划 | 在 `GMatchWorker.h` 保存起始三元组、查询端点角色、计划槽位、两端属性组。冻结连通前缀并重建 `bound_edges`；原有末层排序不能移动锚定位置。固定同一计划进行消融。 | 即使选择了宾语作为遍历起点，数据源端和目标端仍按 RDF 方向识别。 |
| 扫描 | 在计划生成后、启动任务计算前，源顶点所属 rank 从 OUT 邻接表流式枚举起始谓词，校验端点常量、同变量约束和两端间其余已可判定的约束。批量获取必要的远端信息。 | 每个合法的有序双端绑定只产生一次；同一事实的 IN 副本不再发种子。多个首端点间谓词是合取条件；不同变量可以取同值。 |
| 状态 | 在 `Subgraph.h` 的任务子图或 `Task.h` 中保存显式种子列表。每个种子记录有序端点 ID，查询和起始边标识可由任务公共字段提供。同步复制构造、MPI 和磁盘序列化/反序列化。 | `?x p ?x` 只绑定一个计划槽；`?a p ?b` 即便两个数据 ID 相同，仍绑定两个角色。 |
| 路由 | 源 rank 组合双端 sketch，按签名把种子描述符批量发到执行 rank。目的 rank 按完整分组键收集有界批次，再分给本地线程。原数据顶点的 owner 继续负责原有拉取服务。 | 相同逻辑组的候选边可以跨源 rank 相遇；多个分组键可以落在同一机器。分批投递有结束标志及背压；任务总数和种子数分别统计。 |
| 执行 | `GMatchComper.h` 按组取两端所需数据的并集，构造任务子图。`graph_matching.h` 对每条种子预填绑定并从第一个未绑定角色做精确扩展。两端已覆盖全部角色时，验证完全部约束直接贡献一行。 | 共享数据后仍只枚举显式种子，禁止对两个端点集合重新作笛卡尔积。工作窃取以完整批次转移，若拆批则按互斥的种子子集拆分。 |

首边选择沿用当前启发式作为基准。如要改进计划，另记为独立因素。默认比较中固定首边、后续顺序、数据 placement 和 MPI 配置。边种子数可能远高于顶点种子数，须保留现行根任务系统作为实际部署基线。

## 2. 两套可独立评估的签名

**论文对照版。** 固定每个分量的键为 `(查询端点角色, IN/OUT, 谓词)`，从该数据端点的对应邻居 ID 集合取最小哈希，并按计划的稳定顺序拼接。对多标签 RDF，同一邻居可以出现在多个属性组；为不同角色和属性组使用独立随机排列，工程上使用固定且可记录的独立种子近似。只有在相应独立性及 MinHash 假设下，单轮完整 sketch 的碰撞概率才等于各分量 Jaccard 的乘积。多轮整向量完全相等会再次降低碰撞概率。实现采用定义明确的无符号定宽哈希；不同 rank 使用相同种子。有效种子缺少必需分量的邻居时提前筛除。路由哈希可取模，目的地仍比较完整 sketch；哈希碰撞不参与答案判定。

**剩余工作版，优先验证的工程改进。** 建立两个端点在后续计划中真正要访问的属性组，生成剩余工作的边签名。仅被首边绑定用完的约束退出签名；同一谓词若还关联其他未绑定角色，保留相应方向的分量。仅用本地邻接项即可完成的叶子，与需要远程拉取整表的角色分别估价。无剩余工作时直接处理种子，避免签名和迁移。该定义改变了用于相似度计算的集合，应独立标注，不能直接宣称复现原定义。

**先省签名开销，再考虑放宽分桶。** 在端点 owner 上，对本次查询触及的 `(数据顶点, 查询端点角色, 计划版本)` 缓存属性摘要和邻接大小。同一端点出现在多条首边时只生成一次摘要。按目标 owner 批量请求远端摘要；取摘要和取整个邻接表分别计费。避免在分组决策前为每条候选边各拉两份完整邻接表。首版使用单一分组键、单一执行归属。只有当严格碰撞组覆盖太低、而离线可复用量高时，再增加多轮分带候选并做成本复核。多带命中只提名候选组，每条种子最终选一个组；跨 rank 多提名需要唯一协调者，不能向每个命中桶投递可执行副本。

### 在四条 YAGO2 查询上的具体解释

以下例子假设首边分别选为导师、参演或婚姻关系。实验需记录实际计划。Q1 的学生端有姓名、出生地，导师端有出生地；候选城市求交可能很小，而重复获取高频导师邻接表可能很贵。Q2 还要从学生找到配偶并验证出生地，首边两端的局部相似度只能预测一部分后续成本。Q3 若首边为 `?a1 actedIn ?movie`，演员端要取姓名，电影端的 `IN, actedIn` 仍用于找 `?a2`，即使允许 `?a1=?a2` 也不能删掉该分量。此时必须增加按电影 ID 分桶的廉价对照，它天然复用同一部电影的演员列表。Q4 若首边为婚姻关系，则后续主要是两端姓名与出生地。若每端邻域都很小，构造双端签名和路由的成本可能已经超过可避免的扫描。

## 3. 组内究竟共享什么

1. **邻接与网络。** 对同一目的 rank 的同一批次，按数据顶点 ID 去重拉取，复用现有 cache；基线也启用相同的 cache 和在途请求合并。只把真正发送的请求与响应当成网络开销。
2. **候选过滤与扫描。** 在需要时缓存 `(数据顶点, 查询角色, 方向, 谓词, 常量过滤)` 的有序候选列表。先复用最常重访的属性邻域与邻域过滤。不得把不同查询角色的过滤结果混用。
3. **交集或后缀。** 仅当操作数和影响该步的已绑定条件都相同，才共享求交结果。若要在不同端点之间复用内容相同的列表，可用摘要索引再比较完整有序 ID 列表。LSH 碰撞本身不能证明两份中间结果相等。有界缓存优先保留扫描成本高且会再用的条目。缓存计数后缀还须证明剩余查询对未入键的绑定无依赖；首版逐种子保留结果重数即可。

粗略成本模型按时间统一单位。一个合并批次的净收益约等于省下的重复传输字节除以有效带宽，加上省下的邻接扫描/求交时间，再减去取摘要、签名、路由、额外同步与热点排队的时间。簇大小和预计工作内存设上限，重桶用种子 ID 确定性拆批并记录失去的复用。验证时以最慢 rank 的墙钟耗时和实测字节为准。

## 4. 可计算的重复率与一组离线数值

固定批次和计划阶段，令每条种子 e 的精确可复用工作集合为 W(e)，一个工作项 k 的代价为 c(k)。在该阶段、同批次可共享一次时，原本逐种子执行的工作量为 `sum_e sum_{k in W(e)} c(k)`，分组后最低为 `sum_g sum_{k in union_{e in g} W(e)} c(k)`。两者之差是逻辑可省量。分别对拉取对象、属性扫描、相同操作数求交建立工作键；不同类别的次数不能相加为同一种指标。

对候选执行 rank w，可用组内需求频次 n_g(v) 和邻接序列化大小 b(v) 估算冷缓存逻辑机会：对所有 owner(v)≠w 的 v，累加 max(n_g(v)−1,0)×b(v)。这个量假设各单边任务独立取数且固定在 w。正式对照以基线真实路由、共享缓存和新策略的总通信账为准。为避免筛选本身吃掉收益，可以先用摘要提名一小组候选，利用顶点大小和前一批实测缓存命中率估算增量收益，再决定是否并入；相似度相同的两个组应优先选择预计节省更多时间且不会形成热点的组。真实网络字节还取决于执行 rank、本地数据、缓存命中、跨批保留和迁移开销。

例用 `?a p ?b . ?a r ?x . ?b s ?x . ?x t ?y`，固定 p 为首边。32 条一对一的 p 边分成四类，每类八条。令 k 为类号 0 到 3，左端 r 邻域为整数区间 [100k,100k+47]，右端 s 邻域为 [100k+16,100k+63]。每类有 32 个合法 x，每个 x 有一个 y，四类互不相交，正确答案为 1024 行。按工作键 `(x, OUT, t)`，计算各批内部所需的不同扫描次数。端点 ID 独立于这些 x。离线枚举结果如下。

| 分组 | 批次数 | 每批内去重后的 t 扫描次数合计 | 相对逐种子 |
|---|---:|---:|---:|
| 每条边单独执行 | 32 | 1024 | 0% |
| 论文全部属性的完整签名相等才合并 | 32 | 1024 | 0% |
| 随机分四组，每组八条 | 4 | 480 | 53.125% |
| 剩余属性签名，命中后按工作键共享 | 4 | 128 | 87.5% |

随机对照的种子固定为 42，先打乱编号 0 到 31，再连续切成大小为八的批。表中使用每个角色/属性分量各自的稳定哈希，按完整向量相等分组。严格版每条边至少有一个独有的 p 邻居分量；剩余版同类边的两端剩余集合相同。在这个例子里，剩余版比同批量随机分组再少 352 次扫描。如果只分桶而不共享扫描，结果仍须执行逐种子工作；若基线已有跨批缓存，新增可节省量会缩小。负对照令每条边自成一类，所有种子的剩余集合互不相交，则四种分组均需 1024 次扫描。上述是逻辑工作量，不能当作 MPI 时间或 YAGO2、LUBM 的实测降幅。

## 5. 交付顺序与验收

| 里程碑 | 产物 | 决策依据 |
|---|---|---|
| M0 | 现行版本的分 rank 计数器及按首边分层抽样的工作轨迹。保留高频端点和长尾分层，避免只采轻任务。 | 得到候选边数、不同端点数、跨种子重复工作、缓存后仍重复的字节以及最慢 rank 耗时。小批次离线重放用于比较策略；小样本不能直接外推全图耗时。 |
| M1 | 普通边哈希和双端绑定的正确执行器。 | 完整绑定多重集与现行正确版本和小图独立 oracle 一致，包含反向、多边合取、自环、同值双变量、重复事实、常量及无后缀。验证网络发送、落盘恢复、窃取、热桶拆分时每个种子恰好执行一次。 |
| M2 | 定义 5 的双端分属性 QPMH、端点摘要缓存、全局路由及组内共用邻接。 | 专门验证同拓扑不同谓词/方向的区分能力。采样比较完整 sketch 匹配率和实际工作集合重叠；分别监测错误合并和漏掉的高复用对。 |
| M3 | 剩余工作版签名，以及经 M0 确认值得缓存的扫描或交集操作。 | 对相同边种子、相同缓存和预算，检验签名、实际复用量和最慢 rank 时间是否同时改善。较弱结果据实报告，按开销拆解决定是否保留。 |

**对照组。** 保留现行根任务系统作为部署参照。边任务中比较普通边哈希、按单端点归属（例如 Q3 的电影）、同批量随机分组、普通全邻域双端 MinHash、完整 QPMH、剩余工作 QPMH。除不合并的单边参考外，各分组方法使用相同批次容量、局部缓存、精确复用内核和调度预算；随机对照尽量匹配批大小分布。对优胜签名再固定桶成员，开关中间计算共享，区分分组选择与组内执行的收益。当前根合并开关不能代替这一组对照。对相同签名分别允许全局共址，或仅在各 owner 内合并，也能直接检验全局路由带来的额外复用能否覆盖迁移成本。

**运行方法。** 先用可手算的正负对照和现有绑定回归，再以 1、2、4 rank 验证分发和窃取；性能实验沿用实际 12 节点、每 rank 4 线程，按查询单独运行。固定数据、首边、顺序、分区、线程、缓存容量及编译优化；随机化配置运行次序，建议每查询每配置至少五轮配对运行，报告中位数及波动，区分冷缓存、热缓存以及仅在跨查询重复运行时才可摊销的准备开销。采用生产计数路径，完整绑定日志只在小图正确性验证时开启。

**必报指标。** 输出数、种子数与唯一执行数、摘要请求数与字节、路由字节、真正远程邻接响应字节、缓存命中/在途请求合并、实际扫描的邻接项数、求交调用和输入项数、任务峰值内存、每 rank 各阶段时间及端到端墙钟时间。按每条查询报告相对普通边哈希、随机批和现行根系统的成对差异。只有收益超过重复运行波动且端到端时间下降，才据此报告提速；只有工作量下降则报告局部收益。
